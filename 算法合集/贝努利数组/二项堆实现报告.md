# 二项堆（Binomial Heap）从零实现报告

> 本文记录了从零开始实现一个二项堆（也叫二项队列）的全过程，包括关键概念的理解、实现步骤的拆解，以及实现过程中踩过的坑与原因分析。

---

## 一、什么是二项堆

**二项堆**是一种支持高效合并操作的优先级队列，由若干棵**二项树**组成的森林构成，每棵二项树都满足堆序性质（这里实现最小堆）。

### 主要操作复杂度

| 操作 | 复杂度 |
|------|--------|
| `insert` | 摊还 O(1)，最坏 O(log n) |
| `findMin` | O(log n) |
| `extractMin` | O(log n) |
| `merge` | **O(log n)** ← 最大优势 |
| `decreaseKey` | O(log n) |
| `deleteNode` | O(log n) |

相比二叉堆 `merge` 需要 O(n)，二项堆把合并降到 O(log n)。

### 二项树 B_k 的关键性质

- `B_0` 是单节点；`B_k` 由两棵 `B_{k-1}` 合并（一棵的根挂为另一棵的最左孩子）
- `B_k` 共有 **2^k** 个节点
- 根的孩子分别是 `B_{k-1}, B_{k-2}, ..., B_0`（按 degree 降序排列）
- 深度 i 的节点数为 `C(k, i)`（"二项"得名于此）

### 一个 n 节点二项堆 = n 的二进制分解

n 的二进制中有哪些位为 1，堆里就含哪些阶的 B_i。最多 ⌊log₂ n⌋ + 1 棵树。

## 二、整体实现路线

按由易到难的顺序：

1. **Node 节点结构** —— 数据存储
2. **link** —— 把同阶 B_k 拼成 B_{k+1}
3. **mergeRootLists** —— 按 degree 升序归并两条根链表
4. **unionHeaps** —— 在归并链表上消除同阶冲突（核心，最难）
5. **insert** —— 调用 unionHeaps
6. **findMin** —— 扫一遍根链表
7. **extractMin** —— 摘最小根 + 反转孩子 + union
8. **decreaseKey** —— 上浮
9. **deleteNode** —— decreaseKey(INT_MIN) + extractMin
10. **析构函数 + 禁拷贝** —— 防内存泄漏与 double-free

## 三、实现过程中遇到的问题

下面按时间顺序记录每个步骤踩过的坑。

### 问题 1：Node 字段未初始化

**原代码**：

```cpp
struct node {
    private:
        int key;
        int degree;
        node* parent, *child, *sibling;

    public:
        node(int k) : key(k) {}
};
```

**错因**：

1. 构造函数只初始化了 `key`，`degree`、`parent`、`child`、`sibling` 都没初始化，是**野指针**——后续判 `if (x->child)` 会访问随机内存导致崩溃。
2. 字段都设成 `private`，那么作为内部数据结构使用时，外部类（`Binomial`）没法访问字段，编译不过。

**修复**：

- 构造函数初始化所有字段（`degree(0)`，三个指针都设为 `nullptr`）
- 用 `struct` 默认 public，作为内部数据结构无须封装

---

### 问题 2：link 不应比较 key + 丢失 z 的原孩子

**原代码**：

```cpp
static void link(Node* y, Node* z) {
    if (y->degree != z->degree) return;

    if (y->key > z->key) {z->child = y; z->degree++;}
    else {y->child = z; y->degree++;}
}
```

**错因**：

1. **link 不应比较 key**：`link(y, z)` 是无脑挂载操作，调用方已经决定好父子关系，再比较一次会让逻辑混乱。
2. **直接覆盖 `z->child` 会丢失 z 原来的孩子**：z 在 link 之前可能已经有孩子（如 B_2 已经有 2 个孩子），直接 `z->child = y` 会让原孩子丢失。
3. **没维护 `parent` 和 `sibling` 字段**：y 成为 z 的孩子后，需要设 `y->parent = z`，并通过头插法把 y 加入 z 的孩子链表。

**修复**：用"头插法"，先保存 z 原 child 给 y 当兄弟，再让 z 指向 y。

---

### 问题 3：mergeRootLists 中 dummy 用法错误 + 漏接尾巴

**原代码**：

```cpp
static Node* mergeRootLists(Node* a, Node* b) {
    if (a == nullptr && b == nullptr) return nullptr;
    if (a == nullptr) return b;
    if (b == nullptr) return a;

    Node* dummy;
    dummy = (a->degree < b->degree) ? a : b;
    while (a || b) {
        if (a->degree > b->degree) {
            dummy->sibling = b;
            b = b->sibling;
        } else {
            dummy->sibling = a;
            a = a->sibling;
        }
    }
    return dummy;
}
```

**错因**：

1. **dummy 没有移动**：`dummy` 始终指向同一个节点，每次 `dummy->sibling = X` 都覆盖上一次写的，最后只剩一条边。需要用一个**移动的 tail 指针**。
2. **循环条件 `while (a || b)` 内部空指针解引用**：当 `a` 走完变 nullptr 但 `b` 还有，循环体里 `a->degree` 直接崩。应改为 `while (a && b)`，循环外接上剩余。
3. **dummy 选成真节点会破坏其原 sibling**。

**修复**：用栈上 dummy 哨兵 + 移动的 tail 指针 + 循环条件 `&&`，循环外 `tail->sibling = (a ? a : b)` 接尾。

---

### 问题 4：unionHeaps 的指针推进错误（最严重）

**原代码**：

```cpp
static void Union(Node* target) {
    if(!target) return;

    Node *pre = nullptr, *cur = target, *next = target->sibling;
    while (cur && next) {
        if (cur->degree == next->degree) link(cur, next);
        pre = cur;
        cur = next;
        next = next->sibling;
    }
}
```

**错因**：

1. **link 之后无脑推进 cur/next**：做了 link 之后 cur 或 next 已经离开了根链表，但代码还把它们当根继续推进。
2. **没决定"谁当父亲"就直接 link**：可能破坏最小堆性质。
3. **没处理三连同阶**：归并扫描中可能临时出现三个连续相同 degree（如 H1={B_0,B_1}, H2={B_0,B_1} 归并后第一对 B_0 进位后会变成 `B_1, B_1, B_1`），需要让前两个先跳过、让后两个先合并。
4. **没先调用 mergeRootLists**：union 应该先归并再消冲突。

**修复**：实现 CLRS 的 4-case 逻辑，维护 prev/cur/next 三指针：
- case 1/2：阶不同 或 三连同阶 → 整体后移
- case 3：二连同阶且 cur.key ≤ next.key → cur 当父亲吃掉 next（要先 `cur->sibling = next->sibling` 把 next 摘下）
- case 4：二连同阶且 cur.key > next.key → next 当父亲吃掉 cur（要修复 prev 或 head）

---

### 问题 5：insert 返回值搞错

**原代码**：

```cpp
Node* insert(int key) {
    Node* node = new Node(key);
    head = unionHeaps(head, node);
    return head;
}
```

**错因**：

`head` 是合并后整个堆的头（degree 最小的根），**不一定是新插入的节点**。例如插入 5 后再插入 10，合并成 B_1，5 是根，head 指向 5，而不是新插入的 10。

返回错误指针会导致用户后续 `decreaseKey(p, ...)` 时改错节点。

**修复**：返回 `node`（new 出来的新节点指针）。

---

### 问题 6：findMin 直接返回 head->key

**原代码**：

```cpp
int findMin() const {
    return head->key;
}
```

**错因**：

`head` 指向 degree **最小**的那棵树的根，但"degree 最小"和"key 最小"是两回事。

例如先 insert(5)、insert(3)，然后 insert(100)：
- 前两个合并：B_1 根 = 3
- 再 insert(100)：根链表是 [B_0(=100), B_1(根=3)]
- head 指向 100，但最小值是 3

**修复**：扫一遍根链表，记录最小 key。

---

### 问题 7：extractMin 多个 bug

**原代码**：

```cpp
int extractionMin() {
    if (!head) throw runtime_error("heap is empty");

    Node* minNode = head, *temp = head, *prevNode = nullptr;
    int minKey = findMin();
    while(temp) {
        if (minNode->key != minKey) {
            prevNode = minNode;
            minNode = minNode->sibling;
        }
    }

    prevNode->sibling = minNode->sibling;

    Node *cur = minNode->child, *next = cur->sibling, *prev = nullptr;
    while (next) {
        cur->sibling = prev;
        prev = cur;
        cur = next;
        next = next->sibling;
    }
    cur->sibling = prev;

    head = unionHeaps(head, cur);
    return minKey;
}
```

**错因**：

1. **死循环**：`while(temp)` 但 `temp` 永远不变。
2. **没处理 prevMin == nullptr 的情况**：若最小节点就是 head，`prevNode->sibling` 是空指针解引用。
3. **反转孩子链表的 cur 起始可能是 nullptr**：如果最小节点是 B_0 没有孩子，`cur = minNode->child` 为 nullptr，`cur->sibling` 直接崩。
4. **没清孩子的 parent 字段**：孩子要变成根了，parent 应置 nullptr。
5. **传给 unionHeaps 的不是反转后的头**：最后传的是循环结束时的 cur 而不是 prev（反转头）。
6. **没 delete minNode**：内存泄漏。

**修复**：
- 一遍扫描同时找 minNode 和 prevMin
- 摘除 minNode 时分情况处理 head
- 标准三指针反转链表，循环条件 `while (c)`，顺手清 parent
- 反转后用 prevC 与剩余堆 union
- delete minNode 后再返回 key

### 问题 8：decreaseKey 上浮指针没推进

**原代码**：

```cpp
void decreaseKey(Node* x, int newKey) {
    if (newKey > x->key) throw runtime_error("new key is larger");
    x->key = newKey;

    Node* m = x, *n = x->parent;
    while (n && x->key < x->parent->key) {
        int temp = x->key;
        x->key = x->parent->key;
        x->parent->key = temp;
        m = n;
        n = n->parent;
    }
}
```

**错因**：

定义了 `m, n` 两个指针，**但循环里始终用 `x` 和 `x->parent` 比较与交换**。这导致：x 第一次交换到父亲位置后，下一轮还是从 x 开始比，但 x 的 key 已经变成原父亲的 key，比新父亲反而可能更大，循环错误退出。**新值卡在中间层而不是上浮到合适位置**。

**修复**：循环里用 `m, n` 推进，交换 `m->key` 和 `n->key`，每轮结束后 `m = n; n = n->parent;`。

---

### 问题 9：析构函数和拷贝控制放在 private 区

**原代码**：

```cpp
class Binomial {
private:
    // ...
    ~Binomial() {
        destroy(head);
        head = nullptr;
    }

    Binomial(const Binomial&) = delete;
    Binomial& operator=(const Binomial&) = delete;

public:
    // ...
};
```

**错因**：

C++ 中 private 成员外部不能访问。把 `~Binomial()` 设为 private 后，类**根本无法被普通栈对象使用**——`Binomial h;` 都会编译失败，因为编译器要"准备" h 的析构能力但析构是 private。

**修复**：把 `~Binomial`、删除的拷贝构造和拷贝赋值都移到 `public` 区。

## 四、最终实现（带注释）

完整实现见 `binomial.cpp`，主要操作的关键注释已加好。

### 核心思想速记

| 操作 | 一句话 |
|------|--------|
| link | 头插法挂孩子 + degree++ |
| mergeRootLists | 链表归并题（按 degree 升序） |
| unionHeaps | 二进制加法 + 4 case 处理同阶冲突 |
| insert | new 单节点 → 当作小堆 → unionHeaps |
| findMin | 扫根链表取 key 最小者 |
| extractMin | 找最小根 → 摘除 → 反转孩子 → union → delete |
| decreaseKey | 上浮（交换 key） |
| deleteNode | decreaseKey(INT_MIN) + extractMin |

### 几个关键不变量

1. **根链表按 degree 严格升序**
2. **每个节点 `parent == nullptr` ⇔ 它在根链表上**
3. **link 的前置条件：y 已从根链表摘下**
4. **B_k 的根的孩子按 degree 降序排列**（这就是 extractMin 要反转的原因）

## 五、心得

1. **理解"二项"是因为节点按深度的分布是二项式系数 C(k,i)**，不是因为它是二叉的。二项树是多叉树。
2. **左孩子-右兄弟表示法**让多叉树用两个指针就能完整表达，但要分清 sibling 的双重身份：根链表上指下一棵根，孩子链表上指右兄弟。
3. **union 是整个二项堆的核心**，4 个 case 看似复杂，本质就是"二进制加法 + 处理临时三连进位"。
4. **指针推进的不变量比代码量更重要**：union 里 prev 永远是 cur 的前驱、cur 永远在根链表上、next 永远是 cur->sibling，理解这几条循环就清楚了。
5. **decreaseKey 用 swap key 而不是 swap node** 是教学版的简化，生产代码可能要交换节点位置才不会让用户的指针失效。

## 六、语法点学习：**禁拷贝**

### 一、什么是"拷贝"

  在 C++ 里，"拷贝"指两件事：

  1. 拷贝构造（Copy Constructor）

  用一个已存在的对象创建新对象：
```c++
  Binomial h1;
  Binomial h2 = h1;        // 用 h1 创建 h2  → 调用拷贝构造
  Binomial h3(h1);         // 同上, 另一种写法

  void foo(Binomial h);    // 按值传参也会触发拷贝构造
  foo(h1);                 // 这里 h 是 h1 的拷贝
```
  2. 拷贝赋值（Copy Assignment）

  把一个已存在对象的内容赋给另一个已存在对象：
```c++
  Binomial h1, h2;
  h2 = h1;                 // 把 h1 的内容赋给 h2  → 调用拷贝赋值 operator=
```

  注意区分：
```c++
  Binomial h2 = h1;        // 这是拷贝构造 (h2 还不存在)
  h2 = h1;                 // 这是拷贝赋值 (h2 已存在)
```
  写法相似，触发的函数不同。

### 二、编译器默认提供什么

  如果你不写拷贝构造和拷贝赋值，编译器会自动生成默认版本：逐字段浅拷贝——把每个成员变量按位 copy 一份。

  对纯值类型（如 struct Point { int x, y; }）来说，浅拷贝就够了。

  但对 持有指针/资源 的类（比如二项堆 Binomial { Node* head; }），浅拷贝会出大事。

### 三、为什么要禁拷贝（用二项堆举例）

  看默认浅拷贝在二项堆上的灾难：
```c++
  Binomial h1;
  h1.insert(5);
  h1.insert(10);
  // h1.head 指向一片节点
  Binomial h2 = h1;        // 默认浅拷贝: h2.head = h1.head
                           // 两个对象指向同一片节点!
```
  现在 h1.head 和 h2.head 指向同一片节点。问题接踵而至：

  灾难 1：double free（析构时崩溃）
```c++
  {
      Binomial h1;
      Binomial h2 = h1;
      // ... 用 h1 和 h2 ...
  }   // 离开作用域, h1 和 h2 都要析构
      // h1.~Binomial() → destroy(head) → delete 那片节点
      // h2.~Binomial() → destroy(head) → 再 delete 一次同一片节点  ← double free!
```
  double free 是未定义行为，常见表现：程序崩溃、堆损坏、安全漏洞。

  灾难 2：相互干扰
```c++
  Binomial h1;
  h1.insert(5);
  Binomial h2 = h1;
  h2.extractMin();         // 修改了共享的节点链
  // 现在 h1 的状态也被破坏了!
```
  两个对象本应独立，结果一个动作影响两个。

  灾难 3：野指针
```c++
  Binomial h2 = h1;
  {
      Binomial tmp;
      tmp.insert(7);
      h2 = tmp;            // 拷贝赋值: h2.head = tmp.head, 但 h2 原节点没释放 + 共享 tmp 节点
  }                        // tmp 析构后, h2.head 指向已释放内存
  h2.findMin();            // 访问野指针 → 崩溃
```
### 四、禁拷贝的写法

  C++11 提供 ```= delete：```
```c++
  class Binomial {
  public:
      Binomial(const Binomial&) = delete;             // 禁用拷贝构造
      Binomial& operator=(const Binomial&) = delete;  // 禁用拷贝赋值
  };
```
  之后这些代码都会编译报错：
```c++
  Binomial h1;
  Binomial h2 = h1;        // 错误: 调用 deleted 函数
  Binomial h3(h1);         // 错误
  h1 = h2;                 // 错误
  foo(h1);                 // 错误 (如果 foo 按值传参)
```
  错误在编译期就被拦下来，比运行时崩溃好得多。

### 五、什么时候要禁拷贝

  判断标准很简单：类是否管理"独占性"的资源。

  一定要禁拷贝的场景

  1. 持有裸指针 + 自己 new/delete 的类（如二项堆、链表、自定义容器）
  2. 持有文件句柄、Socket、互斥锁、数据库连接
```c++
  class FileGuard {
      FILE* f;
  public:
      ~FileGuard() { fclose(f); }   // 拷贝会导致两次 fclose
      FileGuard(const FileGuard&) = delete;
  };
```
  3. 代表"独占资源"语义的类：std::unique_ptr、std::thread、std::mutex、std::lock_guard 都禁拷贝。
  4. 持有大量内存或希望避免昂贵拷贝的类（性能考虑）

  可以让默认拷贝的场景

  1. 纯值类型（POD 或类似 POD）：Point、Color、Date 等只含基本类型字段的小结构体。
  2. 内部成员都是"值语义"的标准容器：std::vector、std::string 自己已经实现了深拷贝，包含它们的类默认拷贝就够。
```c++
  class Buffer {
      std::vector<int> data;   // vector 会自己深拷贝
  };
  // 默认拷贝构造 OK
```
  应当实现深拷贝而非禁拷贝的场景

  如果业务语义就是"对象内容应该能复制成独立副本"，那应该实现深拷贝而不是禁用：
```c++
  class Binomial {
  public:
      Binomial(const Binomial& other) {
          head = deepCopy(other.head);   // 递归克隆整棵堆
      }
      Binomial& operator=(const Binomial& other) {
          if (this != &other) {
              destroy(head);
              head = deepCopy(other.head);
          }
          return *this;
      }
  };
```
  但写深拷贝麻烦且容易出 bug，很多情况下"禁拷贝 + 提供 move" 是更好的设计。

  六、相关概念：移动语义（move）

  禁拷贝后，对象不能复制，但还能不能"转移所有权"？能，用移动构造和移动赋值：
```c++
  class Binomial {
  public:
      Binomial(const Binomial&) = delete;
      Binomial& operator=(const Binomial&) = delete;

      // 允许移动: 把 other 的资源"过户"到 this, other 变空
      Binomial(Binomial&& other) noexcept : head(other.head) {
          other.head = nullptr;
      }
      Binomial& operator=(Binomial&& other) noexcept {
          if (this != &other) {
              destroy(head);
              head = other.head;
              other.head = nullptr;
          }
          return *this;
      }
  };

  // 之后:
  Binomial h1;
  Binomial h2 = std::move(h1);   // OK: 移动, h1 的资源被偷到 h2
                                   // h1 现在 head == nullptr, 是有效但"空"的对象
```
  这就是 ```std::unique_ptr``` 的设计：禁拷贝、允许移动，表达"独占所有权"。

  七、判断流程总结

  我的类持有"资源"吗？(裸指针、句柄、锁……)
  │
  ├─ 否 → 默认拷贝即可, 什么都不用做
  │
  └─ 是 → 拷贝是否有合理语义？(用户真的想要"复制一份独立的"吗?)
          │
          ├─ 想要复制 → 实现深拷贝 (拷贝构造 + 拷贝赋值)
          │
          └─ 不想要复制 → 禁拷贝 (= delete)
                          │
                          └─ 想支持"转移所有权" → 同时实现移动构造 + 移动赋值

  八、Rule of Three / Five / Zero

  C++ 程序员的经典口诀：

  - Rule of Three（C++98）：如果你需要自定义 析构函数 / 拷贝构造 / 拷贝赋值 中的任何一个，通常三个都要自定义。
  原因：自定义析构往往意味着类管理资源 → 默认浅拷贝必坏 → 也得自定义拷贝。
  - Rule of Five（C++11）：加上移动构造、移动赋值，共五个。
  - Rule of Zero：尽量不要自己管理资源，用 RAII
  工具类（unique_ptr、vector、string），让编译器默认的五个特殊成员函数自动正确。这是现代 C++ 推荐的做法。

  二项堆作为教学场景，因为我们直接用 new/delete 管理节点，所以触发 Rule of Three（自定义析构 + 禁拷贝）。如果用
  unique_ptr 管理节点，就可以走 Rule of Zero——但代码会复杂得多。
